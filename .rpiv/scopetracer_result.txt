# Research Questions: how to build a HACS-structured HA vacuum custom component for the Lefant M1 cloud API

## Discovery Summary
The repo is fully greenfield — a filesystem + git sweep confirms exactly one tracked artifact, `.rpiv/artifacts/discover/2026-09-08_21-11-22_lefant-m1-home-assistant-integration.md` (the FRD, commit `ab8f5dc`, branch `develop`), and nothing else: no `src/`, no `custom_components/`, no `manifest.json`/`hacs.json`/README, no tests, and no `.rpiv/artifacts/plans/` or `research/` dirs to anchor on. Because there is no local code to grep, the anchor sweep is replaced by external-reference targeting: all numbered questions below are answerable from Home Assistant core source + developer docs, the HACS documentation and `hacs/action` validator, and community reverse-engineering projects — with citations using `path:Symbol` notation as look-up anchors. The FRD's Recommended Approach and acceptance criteria fix the contract the research must serve: `custom_components/lefant_m1/` layout, email+password config flow with token stored via HA credential storage, fixed-interval REST polling (30-60s), one `vacuum` entity with state/battery and start/pause/stop/return-to-base, unload/reload without re-auth, and HACS validation passing. Key determinable scope decisions for the design phase: parallel vs sequential refresh semantics of `DataUpdateCoordinator`, aiohttp vs requests for a blocking-free async client, re-auth orchestration on 401, the exact `VacuumEntityFeature` bitmask for the four commands, and HACS's release/versioning requirements.

## Questions

1. Establish the canonical 2026 scaffold for a config-flow-based custom component: what must `custom_components/lefant_m1/__init__.py:async_setup_entry(hass, entry)` do — including catching `ConfigEntryNotReady` from `homeassistant/exceptions.py` and calling `hass.config_entries.async_forward_entry_setups(entry, PLATFORMS)` — and how must `async_unload_entry`/`async_unload_platforms` tear it down so reload doesn't require a HA restart (FRD functional requirement 6)? Trace the `ConfigFlow` subclass in `config_flow.py` (`homeassistant/config_entries.py`): `async_step_user` with voluptuous `vol.Required(EMAIL/PASSWORD)` fields, `async_step_reauth` gated by `source=SOURCE_REAUTH`, and `async_create_entry(title, data)` persisting credentials. This matters because the FRD's acceptance criteria "config flow errors are human-readable" and "reloading does not require re-auth" map 1:1 onto these functions' current signatures, and HA deprecates config-flow patterns regularly.

2. Pin down the polling layer: should the integration subclass `DataUpdateCoordinator` from `homeassistant/helpers/update_coordinator.py`, override `_async_update_data()` to call the cloud client, set `update_interval` to the FRD's 30-60s default, and call `async_config_entry_first_refresh()` once during setup — versus the legacy `async_track_time_interval` scheduling — and what are the current semantics of `async_request_refresh`, `last_update_success`, and failed-update backoff for sequential refresh rounds? Determine whether a single shared coordinator refreshed serially (rather than per-entity timers) can still satisfy "state change reflected within 2 poll cycles" from the FRD, and whether the vacuum entity should expose `_attr_*` values derived from `self.coordinator.data` with `should_poll=False`.

3. Determine the current `vacuum` platform contract in `homeassistant/components/vacuum/__init__.py`: the `VacuumEntity` base class, the `VacuumEntityFeature` IntFlag bits (TURN_ON/TURN_OFF/PAUSE/STOP/RETURN_HOME/BATTERY/FAN_SPEED/STATE and the deprecated `SUPPORT_*` aliases), the `VacuumEntityState` enum values (cleaning/docked/error/idle/paused/returning), and the `_attr_state`/`_attr_battery_level`/`_attr_fan_speed` + `VacuumEntityDescription` attribute-caching pattern. Verify exactly which feature bits must be declared so the four FRD commands work from the standard vacuum card — notably whether "start" is expressed as `VacuumEntityFeature.TURN_ON` and `async_turn_on()` rather than a dedicated start method — since declaring the wrong bits hides dashboard controls.

4. Trace the FRD's "no persistence beyond HA credential storage" claim: is storing the session token in `config_entry.data` via `hass.config_entries.async_update_entry` (persisted in `.storage/core.config_entries`) the sanctioned pattern for non-OAuth2 cloud logins, and does rewriting `entry.data` on refresh risk re-triggering setup? Then map the 401/re-auth cycle: cloud client raises → coordinator/entity observes failure → `hass.config_entries.async_reauth(entry_id, ...)` fires `async_step_reauth` in `config_flow.py` → re-credentials and updates the entry, which the FRD requires to be silent ("expired token mid-run triggers silent re-auth"). Also determine whether the modern `homeassistant/helpers/issue_registry.py:async_create_issue` (repair flow) is the expected surface for surfacing unrecoverable auth failures to the user instead of log spam.

5. Establish what is publicly known about the Lefant cloud protocol before any client code is designed: is the M1's cloud API Midea-style (appKey/appSecret + md5 signature over sorted params + nonce, as implemented in community projects like `midea-local`/`midea-msmart`), which the FRD's decision section flagged as brittle to secret rotation, or proprietary with a simple email+password → token exchange (the FRD's "Authentication scheme" decision prefers token-based)? Identify the login/device-list/state/command endpoints the Lefant app hits, which GitHub/GitLab projects or HA forks already reverse-engineered Lefant (search lefant, lefant-m1, lefant api), and whether M1 shares a backend with budget-vacuum brands such as Vactidy/Magicclean/Coredy. The answer decides whether `config_flow.py` stores a raw password, a session token, or both, and whether re-auth is re-login or token-refresh.

6. Resolve the async HTTP client choice: confirm forbidden/blocking status of `requests` inside HA (event-loop blocking) and the canonical `hass.helpers.aiohttp_client.async_get_clientsession(hass)` wiring from `homeassistant/helpers/aiohttp_client.py`, plus `async_timeout.timeout` request guards, TLS-requirement enforcement (FRD non-functional "TLS for all cloud calls"), and whether the session must be closed explicitly in `async_unload_entry` to avoid leaks across reloads. Determine where transient-error retry belongs — coordinator backoff semantics vs a hand-rolled retry in the client — so HA startup is never blocked by an unreachable cloud (FRD reliability requirement).

7. Define the exact HACS acceptance contract so the "Repo structure passes HACS validation" criterion is decidable: the current `hacs.json` schema (category: integration, name, domains, render_readme, archive, zip_release, hacs min version, homeassistant, filename, content_in_root) from HACS documentation, the full `custom_components/lefant_m1/manifest.json` key set (domain, name, version, requirements, dependencies, codeowners, config_flow, documentation, issue_tracker, integration_type, iot_class, loggers) per the HA developer manifest spec, and how HACS determines version — GitHub release tag `1.0.0`, `manifest.json` `version`, or both. Also verify which checks the `hacs/action` GitHub validator actually runs (manifest validity, homeassistant constraint, no forbidden files) so the repo passes on first push, and whether README/hacs_badge rendering is required for the `integration` category.

8. Determine the config-flow options pattern for user-adjustable polling: does current HA prefer an `options` flow (`async_step_options`/`async_step_init`) storing `CONF_SCAN_INTERVAL`-style numeric seconds in `entry.options`, with runtime mutation of `coordinator.update_interval` in `async_setup_entry`, and what reload semantics apply when `async_update_entry` touches `options` vs `data`? This matters because the FRD hard-codes a 30-60s default interval that users will want to tune without re-entering credentials, and because the choice interacts with Q4's re-auth flow (data rewrites vs options rewrites have different re-setup implications).

9. Define the mock-only testing strategy the FRD mandates (no live device/credentials available): HA's current pytest conventions for custom components — `pytest-homeassistant-custom-component` fixtures (`hass`, `enable_custom_integrations`, `caplog`), mocking the network layer with `aioresponses`/`respx` or a fake cloud-client class, and how the vacuum platform's own unit tests in `tests/components/vacuum/` structure entity tests — plus how to simulate the acceptance scenarios "invalid credentials produce recoverable config-flow error" and "expired token mid-run triggers silent re-auth" at coordinator level (`async_refresh`, asserting `last_update_success`). This is the only verification path available in this environment, so the question is whether the documented test idioms can express a 2-poll-cycle state propagation without a real cloud.
